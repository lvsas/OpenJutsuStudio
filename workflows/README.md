## The two H3 take graphs, and why both exist

They are not duplicates; they answer different questions.

`h3-native-take.api.json` produces a **native take**: it reads a video with its
MCTX capsule, applies pins, samples, and trims/saves back with the capsule
attached (`H3LoadVideoWithMCtx`, `H3MCtxApplyPins`, `H3TrimAndSaveVideoWithMCtx`).
It is compiled by `src/h3_continuity_graphs.py` and used for roots, Swap results
and the native-take paths.

`h3-continuity-latent.api.json` builds a **continuation**: it keeps that same MCTX
take machinery and adds joint audio/video conditioning, context windows and the
audio mask (`H3JointConditioning`, `H3ContextWindows`, `H3JointAudioMask`). It is
compiled by `src/h3_latent_graphs.py` and is the only graph
`src/continuity_pipeline.py` submits when a scene is carried forward.

So the relationship is layered, not parallel: the continuation graph is a
**superset** of the take graph. The take graph must never grow continuation nodes,
otherwise both paths would submit the same work under two names.

Naming the first one `h3-continuity-base` was misleading: on its own it has no
continuation nodes at all. `tests/test_workflow_templates.py` pins the sizes, the
markers and the one-builder-per-template mapping, and checks that every tracked `.api.json`
is submittable on its own, while the one `.template.json` deliberately is not.

## Why these graphs are tracked

The first three graphs are exported from this project's builders (`src/graphs.py`, `src/h3_graphs.py`)
so they stay testable, pinned to the frozen take recipe, and free of the hand-edit drift that makes a
saved workflow and a running app disagree. The exported files are written out so the workflows ship
with the repository and can be read or loaded in API format.

`flux3-klein-official-t2i.json` is intentionally different: it is the tracked **vendor source** for
Viral Character Maker, never regenerated by our export script. `src/character_graphs.py` deep-copies
it, verifies its pinned canonical digest, patches only its declared runtime controls, and appends the
SDK-readable caption saver. Any change to this file is a reviewed workflow migration, not an export.

## Placeholders

Every asset is a named placeholder, and the app substitutes a real asset for each before
submitting:

| Placeholder | Replaced with |
| --- | --- |
| `og-source-frame-placeholder.png` | the reference frame the anchor is built from |
| `og-character-reference-placeholder.png` | the uploaded character reference |
| `og-source-video-placeholder.mp4` | the normalised, padded source clip |
| `og-edited-frame-placeholder.png` | the anchor returned by the image-edit stage |
| `h3-source-placeholder`, `h3-reference-placeholder-<n>` | the prepared H3 source and each uploaded character reference, in order |

## Loading them

They are **API-format** graphs, not UI-format workflow files. Submit them to a ComfyUI
`/prompt` endpoint, or convert them for the canvas. They carry no credentials and no local
paths: the model filenames they reference must be installed on the target ComfyUI, and
`README.md` lists them.
